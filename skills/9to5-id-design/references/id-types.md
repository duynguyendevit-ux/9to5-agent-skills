# ID types

## Database-generated: identity / sequence / auto-increment

**Pros**

- Smallest possible key: ~8 bytes, so the smallest primary-key index and the cheapest
  foreign keys.
- Inserts arrive in order, which keeps index locality ideal.
- No application code, no library, no coordination. The database guarantees uniqueness.

**Cons — the four limits**

| Limit | Mechanism |
|---|---|
| A round-trip is required | The ID exists only after the insert, so parent and child rows cannot be built together in memory |
| Throughput is bound to the database | Speeding up ID creation means scaling the database |
| Multiple writers need manual partitioning | `auto_increment_increment`/`offset`, or Oracle RAC sequence cache and `ORDER`/`NOORDER`; every new writer touches every existing writer's config |
| The counter is a shared resource | Concurrent large transactions queue behind the counter; combined with row locks already held, this is a deadlock source |

**Oracle notes**

- `GENERATED BY DEFAULT AS IDENTITY` (12c+) uses a sequence internally with `CACHE 20`
  by default: values are lost on restart, so gaps are normal rather than a defect.
- In RAC, `NOORDER` is the default and avoids cross-instance contention; `ORDER`
  guarantees global ordering and pays for it.
- Monotonic keys concentrate inserts on the right-most index leaf block. A `REVERSE` key
  index removes that contention but makes the index unusable for range scans, so it is
  not an option for a column you range-query.

## UUIDv4

Completely random 128 bits. Standard libraries everywhere; collision risk negligible.

**The cost is the randomness.** In order-sorted structures a random key means every
insert lands somewhere in the middle: pages split, the structure fragments, and adjacent
logical rows stop being physically adjacent. In InnoDB the table *is* the primary-key
index, so the table itself fragments. In Oracle a heap table does not reorder itself, but
the primary-key index still scatters and grows, and its height increases sooner.

PostgreSQL keeps the table unordered, so tables do not fragment the InnoDB way — but the
index on a random UUID still splits and grows, and WAL volume rises.

**Acceptable uses:** correlation/trace IDs that are never a clustered key, surrogate
columns on low-write tables, anything where uniqueness across disconnected systems
matters more than insert rate.

## Snowflake

64 bits: `timestamp | worker ID | sequence`. The timestamp occupies the high bits, so IDs
increase over time and inserts stay at the end of the index. Two instances cannot collide
because their worker IDs differ; the sequence separates IDs generated within one
millisecond by one instance.

**The obligation nobody mentions:** the whole scheme rests on *each instance having a
unique worker ID*. The ID-generation code is a few dozen lines; issuing, reclaiming, and
never double-issuing worker IDs in a distributed system is the actual project.

- Numbering per deployment does not compose: a service usually runs several deployment
  kinds (API pods, workers, consumers) writing the same database, and an ordinal from one
  StatefulSet is only unique inside that deployment. Hand-splitting ranges per kind
  (API 0-9, worker 10-19, consumer 20-29) is one config slip away from silent duplicates.
- A central ID service reintroduces the arbiter you were removing.
- Pre-fetching ID ranges per instance to reduce that dependency destroys the property you
  wanted: unused ranges leave holes, ranges interleave on write, and the IDs arrive
  unordered — the UUIDv4 write pattern, rebuilt the hard way.

**Choose it when both hold:** you need 8-byte IDs (half of ULID, on every index) **and**
worker-ID issuance is already a solved, operated capability.

## ULID / UUIDv7

48-bit millisecond timestamp in the high bits plus 74-80 random bits. Same order property
as Snowflake, with the random part replacing both worker ID and sequence: two instances
cannot realistically collide within a millisecond, and no instance needs to know another
exists.

| | ULID | UUIDv7 |
|---|---|---|
| Display | 26 chars base32, sortable | 36-char UUID text |
| Monotonic mode | Yes, per generator, within the same millisecond | Not part of the format |
| Standard | Community spec | RFC 9562 (2024) |
| Ecosystem | Libraries in most languages | Native in more and more stacks; PostgreSQL 18 ships `uuidv7()` |

Differences between them are far smaller than the difference between either and the other
two families. Pick by ecosystem fit and stop.

**Caveats:** 16 bytes instead of 8; ordering guarantees are per-generator in the same
millisecond, so do not assume global ordering from an ID comparison; the timestamp prefix
is visible to anyone who reads the ID.

## Summary

| | Width | Ordered | Coordination | Fits |
|---|---|---|---|---|
| Identity/sequence | ~8 B | Yes | None | Single-database, single-writer, internal key |
| UUIDv4 | 16 B | **No** | None | Non-key identifiers, low-write tables |
| Snowflake | 8 B | Yes | Worker-ID issuance | 8-byte constraint + existing infrastructure |
| ULID / UUIDv7 | 16 B | Yes | None | Default for new application-generated keys |

## Four ways this goes wrong

1. **Storing the ID as text.** `CHAR(26)` in `AL32UTF8` can occupy up to 104 bytes; a
   `VARCHAR2(36)` UUID string occupies 36. Store binary (`RAW(16)`), and convert at the
   application boundary. A wider key also widens every foreign key that repeats it.
2. **Constructing the generator per call.** Expensive seeding on every request; with
   Snowflake it produces **duplicate IDs** (same worker ID, same millisecond, sequence
   restarted at zero). With ULID/UUIDv7 it is silent and merely wasteful.
3. **Pre-fetching ID ranges from a central service.** See Snowflake above: it recreates
   the random-write pattern the exercise was meant to avoid.
4. **Exposing the raw ID without deciding what it reveals.** Counters leak business
   volume and invite enumeration; time-ordered IDs leak creation time. Both are often
   acceptable — the failure is not choosing.
