## What follows from that

**Identity primary keys are the mainstream and behave well.** Inserts arrive in order, so
index locality is good. Two Oracle specifics to keep in mind: `CACHE 20` means gaps after
restart are normal, and the right-most leaf block is the hot spot on extreme insert rates
(a `REVERSE` key index would fix that but destroys range scans, so it is the wrong tool
for a key you range-query).

**`outbox_record` is the one table with a random primary key on a high-insert path.**
`outbox_id` is a UUIDv4 string, so every insert lands at a random position in the
primary-key index. The damage is contained to that index — the claim and cleanup indexes
are keyed on `(producer, status, …)` and their insert locality is unaffected, and lookups
by `outbox_id` are single-row. What it costs is index growth and scatter, plus 36 bytes
per key and 72 bytes of text in those two columns per row. Structural, not measured:
confirm with `clustering_factor` below before calling it a problem.

**The mirror tables carry the widest keys.** In Oracle a secondary index stores the
`ROWID`, not a copy of the primary key, so a wide key does not inflate every secondary
index the way it would in InnoDB. The cost sits in the primary-key index and in every
foreign-key column that repeats the value. When a numeric variant already exists in the
same table (`account_facility_id NUMBER(38,0)` next to `facility_id VARCHAR2(255)`) prefer
the numeric one for new foreign keys.

**Nothing in the codebase uses the article's recommendation yet.** Adopting it for new
tables is one library plus a `RAW(16)` convention; converting an existing primary key is a
different order of problem and needs the scope sentence below.

## What to measure

```sql
-- widest identifier columns, which is where the key cost lives
SELECT table_name, column_name, data_type, char_length
FROM   user_tab_columns
WHERE  column_name LIKE '%\_ID' ESCAPE '\'
ORDER  BY char_length DESC
FETCH FIRST 20 ROWS ONLY;

-- is a random primary key actually hurting this table?
SELECT index_name, blevel, leaf_blocks, distinct_keys, clustering_factor
FROM   user_indexes
WHERE  table_name = 'OUTBOX_RECORD';

-- index versus table footprint
SELECT segment_name, segment_type, ROUND(bytes/1024/1024, 1) AS mb
FROM   user_segments
WHERE  segment_name IN (SELECT index_name FROM user_indexes WHERE table_name = 'OUTBOX_RECORD');

-- identity/sequence cache behaviour
SELECT sequence_name, cache_size, order_flag
FROM   user_sequences
WHERE  sequence_name LIKE '%OUTBOX%';
```

`clustering_factor` is the honest number for insert disorder: close to the row count means
the index order and the table order have drifted apart, which is what random keys cause.

## Rules for a new table

| Situation | Key |
|---|---|
| Internal to one database, single writer, no external consumer of the key | `NUMBER GENERATED BY DEFAULT AS IDENTITY` — matches 68 existing declarations and costs ~8 bytes |
| Key must exist before insert, crosses a service boundary, or identifies an outbox/event row | Application-generated time-ordered ID: ULID or UUIDv7 in `RAW(16)`. Not `VARCHAR2(36)` for new tables; keep the string form for logs and API responses |
| Mirror of an external system's table | Keep the source key type. Do not migrate it; just avoid new foreign keys on the wide key when a numeric surrogate exists |
| Anything write-heavy | Never UUIDv4 and never `SYS_GUID()` as the primary key |

## Cost of changing an existing key

A primary-key change is a migration that touches: every table holding a foreign key to it,
every index on those columns, every code path that formats or parses the value, and every
API contract that exposes it. On a live table that is a multi-step migration with a
dual-write window. State that scope before proposing it; "switch the PK type" is not a
task, it is a project.

The reverse is also true: for a stable existing system running on identity keys, the
correct recommendation is usually to leave it alone and apply these rules to what is
added next.
