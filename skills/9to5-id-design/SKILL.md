# ID Design

Two questions decide everything about an ID column:

> **Who generates it, and is it still ordered by time?**

Everything else — storage width, index cost, coordination infrastructure, what leaks
to the outside — follows from the answers.

## The four families

| Family | Generated by | Time-ordered | Cost |
|---|---|---|---|
| Identity / sequence | Database | Yes (gaps, not gaps-safe) | A round-trip to the database before the ID exists |
| UUIDv4 | Application | **No** — fully random | Random inserts into the primary-key index |
| Snowflake | Application | Yes | Requires unique worker IDs, i.e. infrastructure you operate |
| ULID / UUIDv7 | Application | Yes (48-bit time prefix) | 16 bytes instead of 8 |

Detail, sizes, and the failure modes of each: `references/id-types.md`.

## What the database-generating family actually costs

Four limits, none of which appear while the system is small:

1. **You must ask the database for the ID.** A parent row and its children cannot all
   be built in memory; the parent insert returns first, then the children follow.
2. **ID throughput is bound to database throughput.** There is no way to speed up ID
   creation alone.
3. **Multiple writers need a hand-managed partition** of the number space
   (`auto_increment_increment` / `auto_increment_offset`, or sequence cache sizing and
   `ORDER`/`NOORDER` in Oracle RAC). Every added writer means touching every other
   writer's configuration, and one wrong node means colliding IDs.
4. **The counter is a shared resource.** Small inserts rarely notice; concurrent
   transactions that each write thousands of rows queue behind it, and combined with
   the row locks they already hold, that is how deadlocks start.

The counter-argument is equally real: an 8-byte database-generated key makes the
smallest possible index, and the writes arrive in order. Choosing an application-side
ID is a trade, not an upgrade.

## Selection rules

- **The ID must be known before the row is inserted** (parent and children written in
  one transaction, an aggregate assembled in memory, an event keyed before commit) →
  application-generated.
- **Several services or instances write the same table without a central arbiter** →
  application-generated. Otherwise you are rebuilding the arbiter.
- **The ID crosses a service boundary** (outbox rows, events, external API) → it must
  not be a per-database counter; another service cannot interpret or reserve it.
- **The table is internal to one database, single writer, nothing external ever sees
  the key** → an identity/sequence column stays the cheapest correct answer. The four
  limits above are the boundary to watch, not a reason to pre-emptively migrate.
- **Never use a fully random ID (UUIDv4, `SYS_GUID()`) as the primary key of a
  write-heavy table.** Random inserts scatter index blocks and fragment the structure
  the index is built to keep ordered. It is not a correctness problem, it is a
  permanent write-amplification tax.
- **Time-ordered application IDs (ULID, UUIDv7) are the default when you leave the
  database.** They need no coordination, keep insert locality, and cost 8 extra bytes.
- **Snowflake only if both conditions hold:** you need 8-byte IDs *and* you can answer
  "who issues a worker ID, who reclaims it, and which deployment gets which range?" If
  either answer is missing, the operational cost is larger than the storage saving.

## Storage

| Choice | Width on Oracle | Verdict |
|---|---|---|
| `RAW(16)` | 16 bytes | Correct for ULID/UUIDv7 |
| `VARCHAR2(36)` | 36 bytes | Compatibility only; doubles the key width |
| `CHAR(26)` | up to 104 bytes in AL32UTF8 | Worst: fixed width, character semantics |
| `NUMBER` identity | ~8 bytes | Cheapest, database-generated |

On Oracle, a secondary index stores the `ROWID`, **not** a copy of the primary key, so
a wide primary key does not inflate every secondary index the way it does in InnoDB.
The costs land elsewhere: the primary-key index itself, every foreign-key column that
repeats the value, and every index on those foreign keys.

## Generator rules

- **One threadsafe generator per application, created once at startup.** A generator
  built per request burns CPU on seeding, and with Snowflake it is worse than waste:
  parallel generators share a worker ID and a millisecond, so they emit **identical
  IDs** and the duplicate only appears under load.
- For ULID/UUIDv7, per-request construction stays silent — the random bits still make
  IDs unique — so the bug shows up as unexplained CPU, not as errors.
- Keep the DB form (`RAW(16)`) and the log form (26-char string) as two functions on
  the same class; never let the string form become the stored form.
- For Oracle identity columns, know the cache: `CACHE 20` by default, so values are
  lost on restart by design (gaps are normal, not a bug). In RAC, `NOORDER` is the
  default and avoids inter-instance contention; `ORDER` gives global ordering at a
  cost. Reverse-key indexes remove right-most leaf contention on monotonic keys but
  destroy range scans — do not apply them to a key you range-scan.

## Exposure

Before an ID reaches an API, URL, or log line, answer what it reveals:

- **Database-generated counters leak business scale.** Two IDs from two days of orders
  subtract to orders-per-day, and predictable IDs invite enumeration and IDOR.
- **Time-ordered application IDs leak the creation timestamp.** Usually acceptable —
  the point is to decide it, not to discover it.
- Obscuring the identifier at the API layer (opaque token, per-tenant hash) is
  independent of the primary key and needs no migration.

## Workflow

1. **Read the schema**, not the ticket: which column is the key, what type and width is
   it, and is it database- or application-generated.
2. **Find the producer** in code: identity/sequence, `UUID.randomUUID()`, `SYS_GUID()`,
   a ULID library, or a hand-rolled Snowflake. Also find its lifetime — static, bean,
   or constructed per call.
3. **Classify** against the selection rules above and state which limit is being hit, if
   any. A review that says "modern systems use UUID" is not a review.
4. **Check the storage width** against the table and its foreign keys.
5. **Check exposure** if the ID is reachable from outside.
6. **Recommend** with the cost of the change: a key change is a migration touching
   every table that references it, every index on it, and every code path that formats
   it. Do not propose one without that sentence.
7. **Hand the DDL to `9to5-sql-migration`**; check index consequences with
   `9to5-oracle-index`.

## Review checklist

| Check | Fail looks like |
|---|---|
| Generator is application-scoped and threadsafe | `new UlidFactory()` inside a request handler |
| Random ID is not a write-heavy primary key | UUIDv4 or `SYS_GUID()` PK on a high-insert table |
| Application ID is stored in binary form | `CHAR(26)` or `VARCHAR2(36)` holding a ULID |
| Snowflake has a worker-ID owner | "we'll figure out the worker ID later" |
| Time-ordered claims verified | assuming ULID ordering across generators in the same millisecond |
| Exposure decided | counter visible in a public URL |
| Change cost stated | "just change the PK type" with no migration scope |
